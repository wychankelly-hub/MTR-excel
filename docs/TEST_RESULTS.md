### 資料庫用量（一場完整課堂模擬，HTTP，PostgreSQL）
20 名學生（4+4+3+3+3+3）、5 關、每格一個作答請求（最壞情況，30% 先輸入錯誤再更正）、210 個提交、10 次提示、180 次投影狀態回報，共 1,359 個 HTTP 請求：

| 項目 | 對照（同一程式，只把分段關掉，即整個比賽紀錄一個值） | 現在（分段） |
|-|-|-|
| 寫入交易次數 | 1,063 | 1,078 |
| 寫入資料量 | 45.2 MB（平均每次 43.5 KB） | **14.9 MB（平均每次 14.2 KB）** |
| PostgreSQL WAL | 12.9 MB | **4.9 MB** |

- 比賽完成後資料約 **0.4 MB**（19 行；最大一行 57 KB）；表格大小（VACUUM 後）約 4 MB。Neon Free 1 GB 足夠存放數以百計場比賽。
- 伺服器重新啟動時由資料庫讀取 0.36 MB；網站的健康檢查（定時喚醒）不讀取資料庫。
- 舊做法中，一個 282 個提交的比賽紀錄約 430 KB，其中提交紀錄佔 375 KB（87%）；現在每次只寫入比賽核心及最新一段（每段 25 個提交）。
- 投影畫面每 15 秒的狀態回報不再寫入資料庫。

### 這一輪發現並修正的問題
- 回覆學生「已核實」時結果仍在 0.15 秒的寫入延遲內，伺服器在這段時間當機會遺失已回覆的答案 → 改為先寫入才回覆。
- 學生端只對網絡錯誤重試約 3 秒，不會重試雲端平台重新啟動時的 502／503 → 改為對網絡錯誤及 502／503／504 以同一 Key 重試約 3 分鐘。
- 伺服器離線期間關卡時間照樣流逝 → 重新啟動後自動暫停並補回。
- 重新部署時新舊實例可能互相覆蓋 → 加入實例接手（fencing）。
- 老師控制台切換到另一場比賽後，劇情字幕不同步（舊比賽的音訊序號較大，令新比賽的劇情被當作已播放）→ 切換比賽時重設序號。

## 開發期間測試找出並已修正的問題
- L2：當 0 人流時段剛好在第 2 列，「只加 B 欄」的錯誤公式在 D2 會巧合正確 → 生成器禁止 0 人流時段位於第 2 列並加入約束檢查；`generate` 亦會在 Preflight 未通過時自動以新 Seed 重抽。
- 全形括號 `（` 的回饋不夠清楚 → 解析前先找出非半形字元。
- 前端 `h()` 把數字 0 當作屬性而不顯示；投影端「啟用聲音」視窗因 CSS 不能隱藏；教師頁三處括號錯誤 → 已修正並由瀏覽器測試覆蓋。
